# BEAT → RELAY protocol v2
Dedicated AU MIDI output cable 2: RELAY Control. Existing cables 0 AUM Control and 1 Circuit Projects keep their identity and messages. Connect only to the future RELAY instance, never hardware.
67 bytes: F0 7D 42 34 52 02, kind, serial (4 little-endian 7-bit groups), program+1, previous+1, flags, loopBars, fadeBars, then five doubles encoded as 10 little-endian 7-bit groups each, F7.
Flags: bit0 valid musical context; bit1 host moving; bit2 phase known; bit3 outgoing/current RELAY enabled. Doubles: observed host beat, outgoing/current song origin, effective activation beat, bar length in quarters, BPM. Double bits use IEEE754 binary64 (not host byte order on wire). Kind1 snapshot; kind2 effective transition. Program indices 0..63, -1 encoded 0. Serial wraps at 28 bits.
Kind2 carries OUTGOING settings and origin, previous/next PC, and effective transition beat after QUEUE. Kind1 carries current settings and origin. Initial activation or activation while stopped is state only. Duplicate confirmations do not emit kind2. An explicit forced same-PC SET restart is a new cycle.
Snapshots on settings/transport/origin changes and at least once per quarter note while rendering. A receiver must also use its AUM musical context; packets are not an independent clock. STOP/invalid callbacks revoke phase readiness. On play/rewind, origin is re-established from the host bar boundary. The receiver must invalidate capture on transport discontinuities, missing packets or changed loop settings.
Timing limitation: events are emitted during the existing render-block activation; queued actions carry the intended boundary even if the host callback passes it slightly. External confirmation uses the observed callback beat. Sample-exact Circuit audio latency and PCH confirmation timing remain physical-test requirements. Output failure is logged, not proof of receiver acknowledgement. No audio processing or seamless claim is made by this BEAT-only candidate.

User requirement: a PCH while host STOP never triggers RELAY or a fade. It updates configuration only; no kind2 transition is sent.

V0.5.26: kind3 forces immediate safe live and cancels any pending loop/fade; it never starts a fade. Its enabled and phaseKnown flags are false. A receiver must process cancellation even if it previously saw kind2 with the same serial. Deduplicate successful kind2 retries by serial within an instance/session epoch.
Sender keeps one fixed-size pending event, including its outgoing settings, origin and serial. At most one attempt per render buffer; three attempts on kind2, then kind3; kind2 expires after 100 ms or on STOP/invalid context/rewind. Three failed kind3 attempts are dropped and latched in diagnostics. A new PCH superseding an unresolved event produces safe-live kind3. Snapshots are suppressed until the pending event is resolved or dropped. No receiver acknowledgement is implied by noErr.
PCH confirmations now include their valid in-buffer event offset in effectiveBeat. QUEUE boundary metadata remains unchanged; hardware/audio latency still needs physical validation.
