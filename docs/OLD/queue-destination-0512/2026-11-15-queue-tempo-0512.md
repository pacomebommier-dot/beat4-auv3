# BEAT 0.5.12: destination queue and independent tempo transition
Approved in conversation: incoming destination owns queue, never outgoing project.
Unknown pcMode -1 ignores unsaved global selector: strict next bar + one full bar.
Saved mode0 immediate; mode1 fourth strict future bar boundary; mode2 first strict future bar.
STOP selects immediately and recalls target BPM immediately.
Playing: start ramp at selection, current host BPM -> destination saved BPM.
Distance <=10 BPM uses one host bar; >10 uses two host bars. Continue past project activation.
Modes only determine queue; no effect on ramp duration. Absent BPM means no tempo command.
Latest destination replaces prior queue/ramp; touching active cancels pending/ramp.
Incoming 64..127 PCs are queue requests and must resolve from AUM timeline without phase deadlock.
Incoming 0..63 is confirmation of actual Circuit activation: update active immediately and never echo PC;
if it confirms our pending/current project, preserve its existing ramp.
Missing timeline defers selection as uncertain until a valid moving timeline returns, then schedule.
Backward seek reschedules pending selection and cancels previous tempo ramp; STOP clears pending/ramp.
Legacy queue memory stays persisted but no longer overrides the new saved mode rules.
No new app UI layout. Existing SAVE persists destination's pcMode. Document mode semantics and queue display.
